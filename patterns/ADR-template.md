## ADR Writing Checklist (Niamaia Enforces)

- [ ] **Numbered sequentially** (ADR-001, ADR-002, ...)
- [ ] **Short title** in filename (kebab-case, max 5 words)
- [ ] **Status** is one of: Proposed/Accepted/Superseded/Deprecated
- [ ] **Context** explains WHY, not just WHAT
- [ ] **Decision** is concrete and actionable
- [ ] **Consequences** include Positive, Negative, AND Risks
- [ ] **Alternatives** table has ≥ 2 options with specific rejection reasons
- [ ] **Implementation Notes** cover migration, POC, dependencies, breaking changes
- [ ] **Follow-up** has review date and measurable metrics
- [ ] **References** are real links (not placeholder)
- [ ] **Index updated** (`docs/adr/README.md`)

## When to Create an ADR (Mandatory)

| Category | Examples |
|----------|----------|
| **Tech Stack** | New language, framework, database, message broker, cache, auth provider |
| **Architecture** | Monolith → modules, sync → async, REST → gRPC/tRPC, event-driven adoption |
| **Data** | Sharding strategy, read replicas, multi-tenancy model, migration strategy |
| **API** | Versioning strategy, breaking change policy, contract testing approach |
| **Security** | Crypto library, key management, threat model changes, compliance scope |
| **Infrastructure** | Cloud provider, K8s vs serverless, deployment topology, secrets management |
| **Observability** | Logging format, tracing implementation, metrics stack, alerting philosophy |
| **Cross-cutting** | Feature flag system, config management, error handling, logging standards |

> **Rule of thumb:** If reversing the decision later would take > 1 week of engineering effort → **ADR required**.

## ADR Lifecycle

```
Proposed → (Discussion + Review) → Accepted → (Implementation) → 
  → (6 months / context change) → Review → 
    → Accepted (continue) | Superseded (by new ADR) | Deprecated (obsolete)
```

### Review Process (Quarterly)
1. **Niamaia** pulls all Accepted ADRs
2. **Check context** — scale, team, requirements, tech landscape changed?
3. **Check metrics** — are follow-up metrics being met?
4. **Decide** — continue, supersede, or deprecate
5. **Update status** and index

## Example: ADR-001 (Filled)

### ADR-001: TypeScript Strict Mode for All Packages

**Status:** Accepted

**Context:**
- Current codebase has mixed TypeScript configs (some strict, some not)
- Recent production bugs caused by implicit `any` and missing null checks
- Team agrees on strict mode but migration effort estimated at 2-3 weeks
- New packages default to non-strict in some templates

**Decision:**
- Enable `strict: true` in root `tsconfig.json` and all package `tsconfig.json`
- Disallow `any` — use `unknown` + type guards or `@ts-expect-error` with justification comment
- Migrate existing code incrementally: one package per sprint, with tests
- New code MUST pass strict check in CI (gate)

**Consequences:**

**Positive:**
- Catches entire class of runtime errors at compile time
- Improves refactoring confidence
- Enables better IDE support and inference
- Aligns with industry best practices

**Negative:**
- Initial migration effort (~3 weeks team time)
- Some third-party types may need `@types` upgrades or local declarations
- Build fails on previously ignored errors (temporary friction)

**Risks:**
| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| Migration blocks feature work | Medium | High | Dedicate 20% capacity per sprint; pair junior devs with seniors |
| Third-party types missing | Low | Medium | Contribute upstream or maintain local `declarations.d.ts` |

**Alternatives Considered:**
| Alternative | Why Rejected |
|-------------|--------------|
| Per-package opt-in | Creates inconsistency; new devs confused; CI can't enforce globally |
| `strictNullChecks` only | Misses other strict benefits (implicit any, bind, this, etc.) |
| ESLint rules instead | TypeScript compiler is source of truth; ESLint can't catch all type errors |

**Implementation Notes:**
- Migration order: `shared` → `core` → `features/*` (leaf first)
- Use `tsc --noEmit` in CI as gate
- `@ts-expect-error` allowed ONLY with `// Reason: [explanation]` comment
- Update `CONTRIBUTING.md` with strict mode guide

**Follow-up:**
- **Review Date:** 2025-04-15
- **Metrics:** 
  - `any` count in codebase (target: 0 in new code, < 50 total)
  - TypeScript errors in CI (target: 0)
  - Build time impact (target: < 10% increase)
- **Rollback Trigger:** Migration velocity < 1 package/sprint for 3 consecutive sprints

**References:**
- [TypeScript Strict Mode Docs](https://www.typescriptlang.org/tsconfig#strict)
- [Effective TypeScript Item 53](https://effectivetypescript.com/)
- ADR-005 (ESLint/Biome config) — related linting decision
```
